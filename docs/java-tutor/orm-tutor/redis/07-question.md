# Redis 三大缓存杀手：穿透、击穿、雪崩

> 用“商场前台（缓存）和后台仓库（数据库）”的比喻，一次性理清它们的攻击目标和防御策略。

---

## 1. 缓存穿透（查“不存在”的东西）

**场景**  
黑客故意拿着不存在的商品编号（如 `ID = -1`）查询。前台（缓存）翻不到，后台（DB）也翻不到。每秒几万次请求直接绕过缓存，击垮数据库。

**后果**  
数据库压力剧增，甚至被打死，缓存完全失效。

**解决方案**

- **缓存空对象**  
  第一次查不到时，在缓存中记录“这个ID不存在”（`value = null`，过期时间设短）。下次请求直接拦截。

- **布隆过滤器（Bloom Filter）**  
  在缓存前加一道“安检门”。启动时将所有可能存在的数据ID存入布隆过滤器。查询时先问过滤器：  
  - 回答“肯定不存在” → 直接拦截，不查缓存。  
  - 回答“可能存在” → 允许查缓存和DB。

---

## 2. 缓存击穿（查“正好失效”的热点Key）

**场景**  
某个超级爆款商品（如春运火车票）缓存到期失效。就在失效瞬间，成千上万用户同时请求该商品，全部涌入DB。

**后果**  
瞬时高并发压垮数据库。

**解决方案（核心：只让一个人去干活）**

- **互斥锁（Mutex Lock）**  
  缓存失效时，第一个请求线程获取**分布式锁**，然后去DB查数据并重建缓存。其他线程发现锁被占用，则自旋等待，缓存重建后直接取缓存。

- **逻辑过期（永不过期）**  
  不设置物理过期时间，而是将“逻辑过期时间”存入Value。线程发现逻辑过期后，异步去后台更新缓存，旧数据先顶着用（适用于能接受短暂不一致的场景）。

---

## 3. 缓存雪崩（“大面积”集体失效 / Redis宕机）

**场景**  
大量缓存Key在同一时间集体过期（如双11运营给所有活动商品设相同过期时间）；或Redis服务器宕机。

**后果**  
海量请求直接砸向DB，数据库被压垮，系统瘫痪。

**解决方案**

- **过期时间加随机偏移**  
  设置过期时间时，在基础时间上加随机数（如 `30分钟 + 随机0~5分钟`），避免Key同时过期。

- **高可用 + 熔断降级**  
  - 部署Redis哨兵或Cluster集群，防止单点宕机。  
  - 若Redis真挂了，使用本地缓存（如Ehcache）或限流组件（Sentinel/Hystrix）熔断降级，返回默认兜底数据，保护DB。

## 秒杀区别口诀（记忆版）

| 问题 | 数据特征 | 本质 | 防御重点 |
| ------ | --------- | ------ | ---------- |
| **穿透** | DB里也没有 | 恶意攻击 | 拦截不存在请求 |
| **击穿** | DB里有，但热点Key过期 | 瞬间爆点 | 串行化重建缓存 |
| **雪崩** | 大量Key同时失效或Redis宕机 | 规模性灾难 | 分散过期时间 + 高可用 |

---

## 生产环境三板斧

优先落地以下组合，可挡住绝大部分缓存灾难：

1. **布隆过滤器** → 防穿透  
2. **过期时间 + 随机值** → 防雪崩  
3. **热Key互斥锁** → 防击穿
